# Data Model

The authoritative schema is `src/db/migrations/*.sql` (34 tables in `001_initial.sql`, validated
with the SQLite CLI). This document explains the entities, relationships and rules.

## Conventions

- IDs are app-generated, time-sortable strings with a type prefix (`prd_…`, `ver_…`, `job_…`).
- Timestamps are ISO-8601 UTC strings. JSON columns contain JSON text validated in code.
- Foreign keys are enforced (`PRAGMA foreign_keys = ON`); WAL journal mode.
- Every migration runs inside a transaction after an automatic database backup and is recorded
  in `schema_migrations` with a checksum; a changed checksum of an applied migration aborts start.

## Identity rules

- **Product** = durable identity (slug, title, type, taxonomy). It never stores files.
- **Product version** = one concrete realisation (spec + content + rendered assets + QA). Versions
  are immutable once rendered; edits, revisions and regenerations create new versions linked by
  `parent_version_id` and `origin`. The previous version becomes `superseded`.
- **Assets** belong to a version; each has role (`deliverable`, `preview`, `listing_image`,
  `source`, `internal`, `export`), sha256, size, and dimensions/page counts where relevant.
- **Listings** belong to a version and a marketplace (unique pair). One product therefore has many
  versions, file formats, bundles and listings, each independently tracked.
- **Bundles** are products of type `bundle`; membership is `bundle_items`; the relationship is
  mirrored in `product_relationships(kind='bundle_member')` for discovery.
- **Variations** are separate products linked by `product_relationships(kind='variation_of')`
  with the varied axes recorded in `details`.

## Provenance

| Where | What is recorded |
|---|---|
| `product_versions.content_provenance` | generator per content field (`anthropic:<model>` or `deterministic:<library>@<rev>`), seed, prompt hash, revision notes used |
| `generation_runs` | provider, model, purpose, prompt hash, settings, tokens, image count, cost estimate and its basis, status, error, timestamps |
| `assets.provenance` | producing tool (`chrome-pdf@155`, `procedural-svg@1`, `openai-images:<model>`, `exceljs`), source template id + revision, design system id, generation run id |
| `qa_runs` / `qa_results` | every check, severity, outcome and details for every version |
| `audit_events` | user and system actions (approve, reject, edit, publish, settings changes, secret set — never values) |

Packaged products include a `manifest.json` (internal, not in the customer ZIP) carrying this
provenance and checksums. Secrets are never part of any provenance record.

## Evidence kinds

`research_observations.evidence_kind` and every scoring factor use:

| Kind | Meaning | Example |
|---|---|---|
| `measured` | Observed by the operator or from the operator's own data | Own shop sales, a count the operator looked up |
| `external_estimate` | Third-party tool estimate | Imported keyword tool search-volume estimate |
| `model_hypothesis` | Generated by an AI model | AI-suggested opportunity idea or differentiation angle |
| `unknown` | No data | Default when nothing has been recorded |

Performance data uses `source_kind`: `marketplace_api`, `csv_import`, `manual_entry`, `estimate`.
Analytics and recommendations always report which kinds contributed.

## Status machines

**product_versions.stage**: `specified → content_generated → artwork_generated → rendered →
qa_checked → packaged → listing_prepared → ready_for_review` (types skip stages they do not use).

**product_versions.status**: `in_progress`, `ready` (in review), `failed`, `qa_failed`,
`superseded`, `rejected`, `approved`.

**listings.status**: `draft → ready | invalid → export_prepared → published_manual |
published_verified`; also `needs_reconciliation`, `failed`, `retired`. Approval is not a listing
status — it is the existence of a non-invalidated `approval_decisions` row whose fingerprint
matches.

**jobs.status**: `queued → running → succeeded | failed | cancelled` (retries return to `queued`
with `run_after` in the future). Attempts in `job_attempts`.

**plan_runs.status**: `pending → running → completed | partial | failed`, or `missed`.

## Approval fingerprint

`fingerprint = sha256(version.deliverable_hash ‖ listing.listing_hash ‖ marketplace)`.
`deliverable_hash` covers every deliverable file's sha256; `listing_hash` covers title,
description, tags, price, currency, attributes, image and file asset ids. Any material change
produces a different fingerprint; the approval is marked `invalidated_at` and publishing refuses.

## Dedupe and idempotency keys

| Table | Key | Guarantees |
|---|---|---|
| `jobs` | `dedupe_key` unique among `queued`/`running` | No duplicate pipeline work after restarts or repeated requests |
| `plan_runs` | `(plan_id, slot)` unique | A scheduled slot runs at most once |
| `publication_attempts` | `idempotency_key` unique among `started`/`succeeded`/`unknown` | A publish for the same listing + approval can't be started twice; `unknown` blocks retries until reconciled |
| `external_listings` | `(marketplace, external_id)` unique | One local record per remote listing |
| `recommendations` | `fingerprint` unique among `open` | The same recommendation isn't repeated while open |
